01

Overview

这个项目是什么

一个面向后端可靠性的工单 Agent。

当前只自动处理一个闭环：支付记录已经成功，但订单仍是待支付。Ollama 负责结构化分类，其余全部由确定性代码控制。

02

Motivation

为什么要做

这是我开始做“能执行动作”的 Agent 时的项目。它只自动处理一种工单，但审批、暂停恢复和可靠投递都做了实现和测试。

也是从这里开始，我从“让模型直接改数据”，转向“模型只提议、代码来放行”。

03

Challenges

遇到了什么困难

  • 模型能不能决定改哪个订单？如果订单号来自模型输出，一次幻觉就能改到别人的订单。
  • 批准之后，参数或订单被改了审批记录如果只记“同意”，就无法保证执行的就是被批准的那个动作。
  • 等待人工审批时，流程怎么办？审批可能要等很久，流程需要能暂停，也需要能在之后可靠地恢复。
  • Worker 崩溃后重投任务提交后 Worker 崩溃、消息被重新投递，订单不能被修改两次。
04

Architecture

系统怎么设计

  1. 创建工单
  2. →
  3. Agent 分类
  4. →
  5. 查询订单和支付记录
  6. →
  7. Policy Guard
  8. →
  9. 不可变审批 · interrupt
  10. →
  11. 人工批准 · resume
  12. →
  13. 校验后修改为 PAID

LangGraph interrupt / Command(resume) 等待人工审批，支持 SQLite 和 PostgreSQL checkpointer；Transactional Outbox + Celery / Redis 负责投递，late ack、协作式取消。

05

Engineering Decisions

为什么这样设计

  • 订单号永远取自工单绑定字段模型只决定分类，它的输出覆盖不了订单号；权限最小化。
  • 审批绑定工具名、规范化参数哈希、订单版本和过期时间任何一项不符都不执行，批准的就是将要执行的。
  • Transactional Outbox + late ack提交后 Worker 崩溃重投，不会重复修改订单。
  • 没有退款工具，也不宣称支持自动退款没做的能力就不写。
06

Validation

如何验证

90条确定性回归评估
0%未授权写入 / 重复副作用

90 条评估集只代表确定性回归，不是模型质量报告。

07

Lessons

我学到了什么

模型只提议，代码来放行。

同一时期开始的 GroundedAgent 把这条思路推得更远：不只是限制模型能改什么，还要证明它凭什么这样改。
