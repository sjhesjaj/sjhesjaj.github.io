进程在写入后崩溃，如何避免重复建单？

会话存在进程内存里，重启就全丢了。更麻烦的是一个很窄的窗口：退货申请已经写进业务库，进程却在会话记录这件事之前退出。这篇记录我怎么把这个窗口关上，以及怎么证明它真的关上了。

结论
每个业务效果至多发生一次，并在下次启动时补记到会话
验证
9 个真实进程崩溃场景，每个恢复两次结果一致

问题：重启会丢什么

M2 之前，售后服务把每个会话放在 AftersalesService._sessions 里，演示业务库放在临时目录。一次重启会丢掉：

  • 所有会话，包括停在追问上、等顾客回答的会话；
  • 待审批动作和它的 grounding 绑定，于是操作员再也无法批准一个已经提交的退货；
  • 业务数据库本身。

前两项靠持久化就能解决。真正难的是第三类问题：网关已经提交了退货，进程随即退出，会话永远不知道结果。进程内的快照回滚覆盖不到这个窗口。

一个被排除的做法

重启后把对话再交给模型，让它“继续刚才的操作”。这不可接受：模型可能提出一个不同的动作，或者再提交一次。恢复必须是确定性的，不能再调用模型。

为什么只靠 LangGraph checkpoint 不够

我把控制流换成了 LangGraph StateGraph，状态存进 SqliteSaver。但 durability="sync" 只保证检查点在下一个节点运行前落盘，它不能让检查点库和业务库成为一个事务，也不说明一个线程里哪个分支才算“已提交”。所以“是否已提交”必须由产品自己定义。

提交协议：head 和 in-flight marker

每个会话有一个会话文件，里面两个字段总是用同一次原子替换一起写：

{"head": "<已提交的 checkpoint id>",
 "inflight": null | {"checkpoint_id": "...", "idempotency_key": "...",
                     "action_name": "create_return", "args_sha256": "..."}}

head 是唯一被当作“对话”读取的版本；inflight 只在“业务库里可能存在一条 head 还没记录的写入”时出现。恢复时只通过这个 marker 找到那次提交，从不去猜“线程里最新的 checkpoint”。

图编译时设置 interrupt_before=["gateway"]，一个带写入的回合按下面的顺序走：

  1. 停在网关前。图运行到 ground 节点后停下，得到 checkpoint G（已落盘）。
  2. 写 marker。会话文件写入 inflight = {G, 幂等键, 动作名, 参数摘要}。在这之前不可能有业务写入，此处崩溃直接丢弃这个分支。
  3. 执行写入。从 G 继续，网关节点调用一次 start_action。
  4. 提交。同一次原子替换里写入新的 head、清掉 marker。
  5. 再回复 HTTP。

进程在第 3 步之后、第 4 步之前崩溃时，恢复逻辑加载 G，确认它的下一个节点正好是 gateway、幂等键和参数摘要都与 marker 一致，然后只重跑网关节点：如果之前已经提交，核心的幂等键直接返回原来的结果；如果没有，就现在提交，Guard 会重新读取可信状态。全程不调用模型。

服务启动时还会扫描所有带 marker 的会话逐个恢复，所以即使顾客不再回来，这次写入也会被补记，并且可以被审批。恢复本身失败时，会话只返回 recovery_pending（409），不接受任何新回合，绝不越过一个没解决的 marker 开新分支。

验证：在每个提交点真的杀进程

测试不靠产品里的测试开关：在子进程里给某个注入点打补丁，到那一步调用 os._exit(17)。父进程检查退出码、两个 SQLite 库（含 WAL）都通过 PRAGMA quick_check、会话文件能解析，然后在同一个数据目录上连续恢复两次，要求两次的视图、会话文件和业务表完全一致。

崩溃点恢复后
a. 停在网关前，marker 还没写head 不变，下一条消息从头正常运行
b. marker 已写，网关没跑恢复时提交：1 条待审批，无重复写入
c. start_action 刚返回业务表与崩溃时一致，审计出现 action.replay_hit，显示真实结果 WAITING_APPROVAL
d. 同 c，只靠启动扫描没有任何请求就清掉 marker；操作员批准后 EXECUTED，1 张回执
e1 / e2. 追问回合写 head 前 / 后前：回到 OPEN；后：顾客的回答接着原来的 run 继续
f. 审批执行后、写 head 前动作 EXECUTED；重复 APPROVE 是幂等重放，仍然 1 张回执
g. 审批的两个事务之间WAITING_APPROVAL 且 approval_recorded = true，操作员再批准一次即可
h. os.replace 之前残留的 .tmp 被忽略，会话停在上一次提交

崩溃模块连续跑三次，每次 9/9 通过。作为反向检查，我在父进程里关掉 marker 恢复，b、c、d 三个场景就会失败，说明测试确实依赖这套机制，而不是碰巧通过。

它不承诺什么

  • 断电和系统崩溃不在范围内。两个 SQLite 库都用 WAL + 默认 synchronous，测的是单进程异常退出。
  • 单进程。不支持多实例同时写同一个数据目录。
  • 审批记下但没执行（场景 g）需要操作员再点一次批准。恢复逻辑不会自己执行已批准的动作，因为执行只能经过 decide 这一个入口，有测试专门守着这一点。

“至多一次”来自持久化的提交记录 + 恢复 marker + 核心的稳定幂等键三者一起，而不是 LangGraph 本身。这是我在这个模块里最想讲清楚的一点。
